# Platform: auth, sync, persistence, deployment

Read when a task touches login, permissions, Firebase, persistence, or deployment.

## Admin access
Per-user login against real Curve Fever Pro accounts.
- **Login**: the only entry point is the "Log in as admin" link on the Tournaments page, which opens `CfpLoginModal` (email and password); the Admin tab exists only while signed in. `AuthProvider.login()` calls the CFP API's `/auth/login` (`src/lib/api.ts`).
- **Authorization**: `auth.shared.ts` allowlists roles `TOUR_ADMIN_ROLE_IDS = [ADMIN, MOD, LEAD_MOD, DEVELOPER, TOUR_HOST, LEAD_TOUR_HOST]`; `canAdminTour(roles)` checks them.
- **Session**: access token in a cookie and `localStorage` (30-day max age). Each SSR request re-validates it against the CFP API (`getInitialAuth`, `server/auth.server-fns.ts`, 60 s in-memory cache).
- **Server-side enforcement**: every privileged write calls `requireTourAdminPermission()` (`tour-permissions.server.ts`), which re-derives the role from the session cookie on the server each time.
- **Reads are public**: `database.rules.json` allows `.read` on every per-tournament root (`tournaments`, `index`, `setups`, `presence`, `media`, below) to anyone. A tournament's id is its access boundary: "hidden" (a draft, a production test run) only means "not listed", so a guessed or leaked id can be read without login.
- There's no dev-mode bypass: the local dev server needs a real login too.
- Legacy admin flags (`curveFFA_admin_unlocked`, `curveFFA_admin_proof_hash`) are deleted on hydrate, and the sync layer drops any legacy `adminProof` field it reads.

## Sync and persistence
- **Layout** (`firebase-paths.ts`, one getter per root), under `environments/{test|prod}/`: the test site and production share one Firebase project and are told apart by the host name.

  | Path | Holds | Written by |
  |---|---|---|
  | `tournaments/{id}` | the `TournamentState`, plus the server-owned `lifecycle` (`status` draft/published/finished, `testRun`, `createdAt`, `finishedAt`) and `started`, `info` (`scheduledAt`, `rulesText`, `screenshots`: image ids) and `annotations` | patch writes; status changes by the lifecycle server functions |
  | `index/{id}` | `TournamentSummary` (`tournament-summary.ts`: title, status, started, test run, scheduled time, created/finished time, format, pooling phase, schedule logic, unit count, and the winners of a finished tournament: `winners` [{ label, members }], written by `finishTournament` from the stored state and cleared by Reopen and Back to draft), a few hundred bytes, read as a whole by the Tournaments page and the Admin list | descriptive fields ride along with each patch; status fields by the lifecycle server functions |
  | `setups/{id}` | the Setup form (`PersistedSetup`), one key per field | per-field patch writes |
  | `presence/{id}/{userKey}` | `{ name, field, at }`: who is in which Setup field | `setSetupPresence` |
  | `media/{id}/{imageId}` | one lobby screenshot as a data URL | the screenshot server functions |

  Every root is public to read and denied to client writes (`database.rules.json`); the Admin SDK bypasses the rules. Rules are not deployed by CI: the organiser deploys them (Firebase console, Realtime Database → Rules, or `firebase deploy --only database`). The rules carry no archive any more.
- **Writes are patches.** The browser never sends a whole tournament. `buildTournamentPatch(previous, next)` (`tournament-patch.ts`) compares the last state known to be stored with the current one and produces a multi-path update at most two levels deep (`scores/r0-rm0-p0`, `title`), values marshalled; a key whose value is empty on either side is written whole, because a child path under a stored empty-value marker would corrupt the read-back. `writeTournamentPatch` and `writeSetupPatch` (`tournament-write.server-fns.ts`) validate the paths (`tournament-write.shared.ts`), plan the update with the pure planners in `tournament-updates.ts` (`planPatchWrite`, `planSetupWrite`; `applyPlan` and `readStoredFacts` in `tournament-store.server.ts`) and apply it as one atomic `update()` that also touches the changed fields of the `index` entry. A finished tournament accepts patches to `annotations` only. A patch never carries the **server-owned** fields: `tournamentId`, `lifecycle`, `started` and `info/screenshots` (`withoutServerOwned`; the server refuses them too). Every privileged server function calls `requireTourAdminPermission()`; `getInitialAuth` and `getLiveBuild` are the public reads.
- **`SyncCoordinator`** (`live-sync.ts`): writer/viewer modes, debounced push (400 ms) of the patch between `base` (the last state known to be stored) and the current state. It sends nothing before the tournament's first snapshot has arrived (every tournament exists in Firebase from "New tournament" on) and never writes a whole tournament. A remote snapshot wins: `scores`/`finalScores` come from it except the keys typed here and not yet sent (`mergeRemoteWriterState`), and every other unsent edit is laid back over the merged snapshot (`keepPendingEdits`), so an echo of an earlier save, or a server write next to the rules text, never takes back what was just typed. `marshalForFirebase`/`unmarshalFromFirebase` protect data Firebase would otherwise lose: nulls in arrays, empty arrays and objects (`{__ffaEmptyArray: true}`, `{__ffaEmptyObject: true}`, `__ffaNull`), and sparse arrays returned as objects. Derived standings tables are stored at round advance and not recalculated per score, which keeps a score's patch to about 25 bytes.
- **`SetupSync`** (`setup-sync.ts`): the Setup form of the loaded tournament, synced the same way into `setups/{id}`, per field. It sends only fields edited here and not yet sent, protects only those from an incoming snapshot (no time hold), and sends nothing before the stored setup has arrived. Two admins editing the same field at the same moment: the last save wins.
- **Lifecycle server functions** (`tournament-lifecycle.server-fns.ts`; rules in `tournament-lifecycle.ts`, `transitionRefusal`): `createTournament`, `publishTournament` (needs a title and a scheduled time), `unpublishTournament` (only before it starts), `startTournament` (Confirm & Start; publishes a draft, fills an empty scheduled time with "now", needs a title, refused a second time via a one-time flag in a transaction, and refused a stale draw before the flag is claimed: `startDrawRefusal` (`start-guard.ts`) judges the stored tournament with the start's patch applied, and the schedule must still seat exactly the roster, as the Schedule preview checks it), `finishTournament`, `reopenTournament`, `returnTournamentToDraft` (keeps id, roster and settings, clears the played rounds), `deleteTournament` (a draft; a test run from any status; clears `tournaments`, `index`, `setups`, `presence` and `media` of the id in one update) and `setTournamentTestRun`. They plan their updates in `tournament-updates.ts` from the few stored facts they need and apply them atomically, with `ServerValue.TIMESTAMP` as the clock.
- **Build check** (`src/features/version/`): `vite.config.ts` fixes one id per build (`__TOUR_BUILD_ID__`, shared by the client and server bundles). A function middleware registered in `src/start.ts` adds it to every server function call as the `x-tour-build` header, and `requireCurrentBuild` (first line of `requireTourAdminPermission`) refuses a call from another build, or with no header, with "A new version of the Tournament Hub is live — reload the page to keep editing." `getLiveBuild` (public GET) returns the server's id. An unlocked admin's tab (`useLiveBuildCheck`) asks it on window focus and when the tab becomes visible (at most once a minute) and every 5 minutes while visible, and shows `NewVersionBanner` with a Reload button when it differs; viewers are not asked.
- **Presence** (`src/features/presence/`): `setSetupPresence({ tournamentId, field | null })` writes `presence/{id}/{userKey} = { name: username, field, at: server time }` (or removes it), where `userKey` is the account id with the characters Firebase refuses in a key replaced. An admin with a tournament loaded announces the control in focus (`PresenceProvider`, named by its element id through `fieldOfControl`), again every 15 s while it stays, and clears it on leaving, on a hidden tab, on closing and on unloading (`PresenceSender`: calls are serialized, a failed one is dropped, and a field that vanished without a blur ends the announcement). Every admin with the tournament loaded subscribes to `presence/{id}` and `.info/serverTimeOffset`, and `activeEditors` lists the others whose `at` is under 30 s old on the database clock. Presence is shown only; it never goes through the tournament's or the Setup form's sync. Viewers never subscribe. Two tabs of one account share one key.
- **Media** (`media/{id}/{imageId}`): lobby screenshots, at most 4 per tournament (`screenshots.shared.ts`). The browser shrinks an image to WebP (longest side 1600 px, under 300 KB; `info/image-shrink.ts`) and `uploadScreenshot` (`screenshots.server-fns.ts`) stores it (server limit 400 KB decoded), then lists its id on `info/screenshots` in a transaction, so two admins uploading at once never go over the limit (the loser's image is removed again). `deleteScreenshot` and `copyScreenshots` (Copy settings) are the other writers; all refuse a missing or finished tournament. A visitor reads an image once and caches it in `localStorage` (`info/screenshot-cache.ts`). The size test (2026-10-13) showed the server and the proxy accept a 2 MB request, so the 400 KB limit is the app's own; in practice a screenshot shrinks to 5-10 KB.
- **Reads**: direct client-side Firebase reads (`firebase-client.ts`): `onValue` for the loaded tournament, the Tournaments list (`subscribeTournamentIndex`) and presence; one-shot reads (`fetchTournamentOnce`, `fetchSetupOnce`, `fetchScreenshotOnce`) for another tournament's data; no login needed.
- **Free-plan figures** (Firebase Realtime Database, 10 GB/month downloaded): before patches every save sent each connected viewer the whole tournament (13.7 KB per score at 43 players; 22 KB at the start of a 67-player qualification + double-elimination tournament, about 63 KB by its Final, about 20 MB per viewer per tournament; four such tournaments a month at 100 viewers is about 8 of the 10 GB). With patches a viewer receives about 80 bytes per score live (22-25 bytes per score patch in replays), a tab switch sends nothing, and a screenshot is downloaded once per browser.
- **What a visitor loads and remembers** (`visit.ts`, `shell/tabs.ts`, `lib/persistence/`): a link `?t=<id>` always opens that tournament; without one `resolveVisit` picks from the list (see `docs/views.md`, "Tournaments"). Browser-only memory: **Exit** `curveFFA_exited` = `{ tournamentId, phase }`; **last tab** `curveFFA_last_view` = `{ tournamentId, tab }` (the old `curveFFA_active_tab` counts only for info, bracket, standings and rankings); the local envelope `curveFFA_state_v1` caches the loaded tournament only, and an envelope without a matching loaded id is ignored.
- **Fallback**: if Firebase is unreachable, `getFirebaseSyncTransport()` returns `null` and the UI shows "Live sync unavailable"; a tournament cannot be loaded then.
- The Firebase client config in `firebase-client.ts` is hardcoded and not a secret. Test, production and local dev all use the same Firebase project.
- **Local dev caution**: opening a real tournament id on the local dev server while its browser holds an admin session makes the app try to write it back; it only fails because no Firebase Admin credentials are configured locally.
- `TournamentState.settings` (optional): the Setup form as typed when a tournament was generated, snapshotted by `generateTournament` (`tournament-settings.ts`) — roster fields excluded, absent on tournaments generated before this field existed. Lets a later tournament copy a past one's settings (`CopySettingsPanel.tsx`, which also copies the rules text and screenshots) without pinning the materialized `gamemodeConfig`/`cfg` numbers to the old headcount.

## Deployment
Hosted on Curve Fever Pro's own infrastructure. `.github/workflows/release-tour.yml` builds a Docker image on every push to `main` or `test` (GHCR tags `latest`/`test-latest`) and deploys it over SSH via Tailscale. The server bundle runs `node .output/server/index.mjs` and needs `FIREBASE_SERVICE_ACCOUNT_JSON` (or Application Default Credentials) plus the CFP API.
- **Production** (`main`): https://tournaments.curvefever.pro/
- **Test** (`test`): https://tournaments-test.curvefever.pro/

After a deploy every admin tab loaded before it must be reloaded before it can write (the build check, above); its banner says so.

Push and login rules: `AGENTS.md`, "Branches and deploys" and "Live checks and login".

**Unconfirmed** (not blocking): how `FIREBASE_SERVICE_ACCOUNT_JSON`/ADC reaches the deploy target, and whether `VITE_API_ENDPOINT` must be set there. Ask the CFP developer who set up the pipeline if a Firebase-write or login problem appears only when deployed.

## Tests
Which checks to run, when and by whom: `AGENTS.md`, "Checks and tests".
- **Line endings**: text files are LF in the index and in every working copy, enforced by `.gitattributes` (`* text=auto eol=lf`), so a plain `pnpm exec prettier --check` passes; no `--end-of-line auto` is needed.
- **Build check**: the pure parts are tested (`build-id.test.ts`, `start-guard.test.ts`, the banner in `NewVersionBanner.render.test.tsx`); the middleware and `requireCurrentBuild` are covered by live checks only.
- **Vitest** (`pnpm test`): the tournament domain layer (`src/domain/tournament/`) has the deepest coverage, one `*.test.ts` per source file in `src/domain/tournament/__tests__/` plus a shared `test-fixtures.ts`. Elsewhere, unit tests are co-located `*.test.ts` files covering pure or near-pure logic: `src/lib/persistence/`, `src/features/sync/` (`live-sync.ts`, `tournament-patch.ts`, `setup-sync.ts`, `tournament-write.shared.ts`), `src/features/tournaments/` (lifecycle rules, update planners, index, visit, Tournaments sections, screenshot validators), `src/features/presence/`, `src/features/info/`, `src/features/auth/auth.shared.ts`, `src/components/ui/`. Domain files import each other widely, so `vitest related` on a domain file usually runs most of the suite.
- **Render check** (`src/features/shell/AppShell.render.test.tsx`, helpers in `test-app.tsx`; `// @vitest-environment jsdom` per file, the global environment stays `node`): renders the real `AppShell` for every fixture of `e2e/screens/fixtures.ts`, as a signed-out viewer and as a Tour Host admin, on every tab `visibleTabs()` lists for that fixture and role (the Admin tab included; rows named `<fixture> · <role> · <tab>`). The admin needs no sign-in: `AuthProvider` trusts an authenticated `initialAuth`. The context is a plain `TournamentContext` value built from the fixture (state, Setup, its list entry, no-op callbacks), so the real `TournamentProvider` (sync, setup transport, presence) and the server functions are not under it; only the presence subscription (`firebase-client`) and `setSetupPresence` are mocked, and jsdom's missing `matchMedia` and `ResizeObserver` are stubbed. Each row asserts that rendering doesn't throw, that `console.error` is never called, that the tab-error fallback is absent, that the page heading shows the fixture's title (not on the Tournaments list), and, on the Players / Rankings tab of a team fixture, that no `teamId` appears as text and every team name does. A `TabErrorBoundary` describe covers the fallback. About 33 s of test time. Build config: `vite.config.ts` loads no plugins when `VITEST` is set, because TanStack Start's plugin gives the components a second copy of React under jsdom (the reasoning is in the log entry on the render check).
- **Not covered**: interactions (clicks, `window.prompt` flows, score entry) and the organiser tools' behaviour, hooks and the real `TournamentProvider`, server functions (`*.server.ts`, `*.server-fns.ts`). Components are rendered by the check above, not exercised.
- **Playwright smoke** (`e2e/smoke.spec.ts`, `pnpm run test:e2e`, which runs the `chromium` project only): seven tests of the signed-out viewer: the Tournaments landing page with no tournament tabs, the "Log in as admin" link opening the login wall, a link to a published tournament opening its Info with the tabs following its phase, switching tabs, the remembered tab across a reload, a link to a tournament that is not there, and a visit without a link loading the only ongoing tournament with Exit sticking across a reload. The tournament list and the live tournament are supplied by the test hooks `window.__CURVE_TOUR_INDEX__` and `window.__CURVE_TOUR_SYNC_TRANSPORT__`. Admin actions are tested by hand, with the organiser signed in. It runs against a local `pnpm dev`, or against a deployed site when `PLAYWRIGHT_BASE_URL` is set (then no local server starts). `vite.config.ts`'s `test.exclude` keeps Vitest away from `e2e/**`.
- **Screenshot spec** (`e2e/screens/`, `pnpm run test:screens`, the `screens` Playwright project; not part of `test:e2e`): opens fixture tournaments as a signed-out viewer and saves full-page PNGs of each viewer tab at 1280 and 390 px to `e2e-screens/<fixture>/<tab>-<width>.png` (git-ignored), plus `bracket-full-1280.png` (the whole rounds row) and the Tournaments list, for comparing the screens with the design boards. The fixtures (`fixtures.ts`) are built with the real domain code (`generateTournament`, `advanceTournamentRound`) from a seeded random source and per-room-distinct seeded scores, so every run draws the same tournaments: 37, 31, 43 and 53 players (qualification table into single elimination, at Round 3, Round 4, the finished Final), a 13-team 2v2v2v2, a 12-team Kings Valley, a 16-player 1v1 double elimination, a 37-player waterfall with a Qual source, long names (37 players, and 13 three-player teams mid-bracket and finished: names, team names and member lines that must wrap), and the before-start ones: `upcoming-info` (37 players, two reserves, rules text, two lobby screenshots served through the browser's screenshot cache) and `upcoming-teams-13` (13 teams of 2), each a roster loaded with `withLoadedRoster` and nothing generated, with the Setup form as `setup` on the fixture; and `drawn-ffa-31`, a generated schedule that is not started. A fixture's list entry (`fixtureIndexEntry`) is described by its own settings and roster, through `buildTournamentSummary`; the Tournaments-list page keeps its own explicit entries. It uses the same hooks as the smoke test and fails on any console error. The viewer needs a running dev server (`pnpm dev`; a cold first start can exceed Playwright's 60 s wait, so start it once beforehand).
