# Curve Fever Pro Tour Hub — Project Handoff Brief

## What this project is
A web app for setting up and running Curve Fever Pro tournaments — organisers load a roster, generate rounds, enter scores, resolve ties, and manage players/teams live during an event; a shareable live link lets everyone else follow the scoreboard, bracket, and rankings as it happens. It replaced a fragile Google Sheets workflow, then (as of **2026-09-10**, see "The rework" below) was itself replaced by a full React/TypeScript rebuild — the original vanilla-JS/HTML app is preserved read-only under `legacy/` and is still the best reference for pre-rework build history and design rationale (see "Using `legacy/` and the pre-rework log" below).

## The rework (2026-09-10)
The entire app was rebuilt from scratch as a React/TypeScript codebase and merged via PR #1 ("rework", `faea942`), landing 28 commits in one go. The old vanilla-JS app was moved to `legacy/` rather than deleted. This was **not a redesign** — it was a faithful, thorough port: every game format, pooling phase, bracket phase, and viewer-facing feature documented in this file's pre-rework history was carried over, including subtle formula-level details (e.g. `fairPoints(rank, score) = rank - score / 100_000`, the corrected tie-break sign from a legacy-era fix, and the multi-game Semis key scheme `r{ri}-rm{rm}-p{pi}-g{g}[-m{mi}]` — both confirmed by reading the new `src/domain/tournament/scoring.ts` directly, not assumed from commit messages). Two things did change materially, on purpose, not as ported behavior:
1. **Admin access.** The old single-shared-password model is gone. The new app authenticates against real Curve Fever Pro accounts (email/password login via the CFP API) and authorizes by account role (`ADMIN`/`MOD`/`LEAD_MOD`/`DEVELOPER`/`TOUR_HOST`/`LEAD_TOUR_HOST`) — see "Admin access" below.
2. **Live-sync writes.** The browser no longer writes straight to Firebase. A write now goes through a server function that re-validates the caller's admin session on the server before touching Firebase — see "Sync & persistence" below.

Deliberately **not** part of the rework: `kings-valley` remained unimplemented at that point (a "coming soon" placeholder in the legacy app too, not a regression; implemented 2026-09-11, see below). No new game format, pooling phase, or bracket phase was added beyond legacy parity.

## Current architecture
- **Stack**: React 19 + TypeScript, TanStack Start (SSR, file-based routing via TanStack Router) + Vite, Tailwind CSS v4, Firebase Realtime Database, `pnpm`. First build tooling this app has ever had — the legacy app had no build step, no linter, no test runner at all.
- **Domain layer** (`src/domain/tournament/*.ts`): the tournament rules engine, ported to pure functions over a typed `TournamentState` (replacing the legacy untyped global `T`), with an injectable `TournamentRuntime` (clock/random/ID source) for determinism. One file per concern — `types.ts` (state shape), `formats.ts` (`GAME_FORMATS` registry), `generation.ts`/`schedule-generation.ts` (bracket building), `pooling.ts`, `single-elimination.ts`/`double-elimination.ts`, `advancement.ts` (tie-breaks, `computeRankings`, cutoffs), `scoring.ts` (Fair Points, `getUnitScore`), `seeding.ts`, `finals.ts`, `rankings.ts`, `roster.ts`, `mutations.ts`, `bracket.ts`, `room-distribution.ts`, `transitions.ts`, `state-defaults.ts`, `runtime.ts`.
- **Feature layer** (`src/features/*`): one folder per tab/concern — `admin/` (`SetupView`, `RunningAdmin` + `RunningAdminRoster`/`RunningAdminScores`/`RunningAdminStatus`), `archive/` (`ArchiveView`), `auth/` (`AuthProvider`, `CfpLoginModal`, `auth.shared.ts`, `server/*.server-fns.ts`), `bracket/` (`BracketView`), `rankings/` (`RankingsView`, `rankings-image.ts`), `scoreboard/` (`ScoreboardView`), `shell/` (`AppShell` — tab bar/nav), `sync/` (`firebase-client.ts`, `firebase-admin.server.ts`, `live-sync.ts`, `tournament-write.server-fns.ts`), `tournament/` (`TournamentProvider` — the app-wide state context).
- **Shared UI** (`src/components/ui/*`): `Badge`, `Button`, `Feedback`, `Form`, `Stats`, `Surface`, `Table`, `Timeline` — the legacy app had no component abstraction at all (template strings + DOM manipulation).
- **Persistence** (`src/lib/persistence/*`): still a pure-`localStorage` fallback, reading/writing the same legacy key `curveFFA_state_v1` — the app works fully standalone, no backend, exactly like before, if Firebase/the server is unreachable. Archive (`archive.ts`) is unchanged in spirit: a separate, local-only, Firebase-independent system.
- **Repo-specific conventions**: `.agents/skills/project-structure/SKILL.md` and `.agents/skills/unslop/SKILL.md` describe general TanStack Start/feature-folder conventions this codebase follows (thin routes, `*.server-fns.ts` naming) — not tournament-domain-specific, more like a style guide.

## Deployment target
The legacy app deployed as static files to GitHub Pages — no server, no secrets, `git push` to `main` was the whole deploy story. **That no longer works** — the new app's `pnpm start` runs `node .output/server/index.mjs` (a Nitro/TanStack Start server bundle), and admin writes require a live server function with access to `FIREBASE_SERVICE_ACCOUNT_JSON` (or Application Default Credentials) plus the CFP API.

**Decided (2026-09-10), live and confirmed as of 2026-09-17**: hosted on Curve Fever Pro's own infrastructure, alongside `api.curvefever.pro`. `.github/workflows/release-tour.yml` (in this repo) handles CI/CD: a push to `main` or `test` builds a Docker image (pushed to GHCR, tagged `latest`/`test-latest` respectively) and deploys it via SSH over Tailscale to CFP's infra — `main` → prod, `test` → the staging target. Confirmed live URLs:
- **Production** (`main`): **https://tournaments.curvefever.pro/**
- **Test/staging** (`test`): **https://tournaments-test.curvefever.pro/** — this is the address used for all live-browser verification in recent `HANDOFF_LOG.md` entries (DNF/no-show tracking, qualAdv fix, Fair Points averaging, etc.).

Branch and push rules, and when to ask the organiser to log in for a live check: see `AGENTS.md`, "Branches and deploys" and "Live checks and login".

**Still unconfirmed** (not blocking): exactly how `FIREBASE_SERVICE_ACCOUNT_JSON`/ADC reaches the deploy target, and whether `VITE_API_ENDPOINT` needs setting explicitly there — worth asking the CFP developer who set up the pipeline if a Firebase-write or CFP-login issue ever shows up only in the deployed environment and not locally.

## Game formats & tournament structure
Full parity with the legacy app (`src/domain/tournament/formats.ts`, `GAME_FORMATS`):
- **`ffa-individual`** — FFA, individual, room size 6–8 (ideal 8).
- **`team-2v2v2v2`** — teams of 2, room size 3–4 (ideal 4).
- **`team-3v3v3`** — teams of 3, room size 2–3 (ideal 3).
- **`team-3v3`** — teams of 3, head-to-head (room size fixed at 2), odd-count strategies `none`/`bye`/`flex`, default `bye` (an unset value means the default, #54).
- **`individual-1v1`** — head-to-head, odd-count strategies `none`/`bye`, default `bye` (an unset value means the default, #54).

**Pooling phases** (`poolingPhase`): `none` (2-round no-elim warm-up), `qual-table` (3 fixed qualification rounds, Fair Points averaged across rounds played), `swiss` (3–7 rounds, fold-pairing, same averaged standings as qual-table — they share one standings engine), `group-stage` (round-robin groups, single or double round-robin, top N per group advance, same averaging) — **both Swiss and Group Stage restricted to head-to-head formats** (`individual-1v1`, `team-3v3`) as of 2026-09-11, gated in both the Setup UI and `generateTournament()`'s validation, since round-robin/fold-pairing always pairs exactly 2 units per room and can't represent a multi-way room shape (FFA/`team-2v2v2v2`/`team-3v3v3`). See "Restrict Group Stage to head-to-head formats" and "Prevent impossible tournament-setting combinations — Stage A" in `HANDOFF_LOG.md`. As of 2026-09-17, a reserve can only be added to a qual-table/Swiss tournament while at most one qualifying round has been completed (`addReserveUnit`, `mutations.ts`) — averaging alone doesn't stop a reserve from winning a spot off a single lucky round, so admission itself is gated instead. See "Fair Points: sum → average, plus a reserve-admission guard for qualification-table/Swiss" in `HANDOFF_LOG.md`. As of 2026-09-18, a qual-table/Swiss tournament can also mark its own leading N rounds as played-but-excluded from the cumulative standings (`excludeFromStandings` on `TournamentRound`, set by `qualificationTablePoolingPhase`/`swissPoolingPhase` via a new "Non-counting rounds (optional)" Setup field) — useful for rounds that exist only to seed the field fairly, not to count toward who advances; `computeQualificationStandings` (`advancement.ts`) skips them, `tieredSeed`'s per-round reseeding is unaffected since it never read the cumulative table anyway. Deliberately scoped to qual-table/Swiss only, not Group Stage. See "Non-counting qualification rounds" in `HANDOFF_LOG.md`.

**Bracket/elimination phases** (`scheduleLogic`): `single-elimination`, `double-elimination` (head-to-head race bracket + grand final), `double-elimination-shared-final` (multi-unit double-elimination feeding one shared Final), **`kings-valley`** (new, 2026-09-11) — a persistent room ladder: rooms ranked top-to-bottom, each round's top finishers in a room promote to the room above, bottom finishers demote to the room below, the middle stays, and only the lowest room with a real match has its bottom finishers actually eliminated. Room counts/sizes are recomputed each round from the shrinking survivor count via the same `distributeRooms()` every other schedule uses; promotion/demotion band sizes are a fixed fraction of room size (`KINGS_VALLEY_MOVE_FRACTION = 0.25`), with a larger fraction (`KINGS_VALLEY_ELIMINATION_FRACTION = 0.5`) concentrated in the bottom room specifically so the format still converges to a Final in a bounded number of rounds (capped at `MAX_KINGS_VALLEY_ROUNDS = 14`) despite only ever eliminating from one room per round. No new Setup field (the organiser tunes nothing, matching "Core value" below). See "Kings Valley" in `HANDOFF_LOG.md`. **Unavailable for head-to-head formats** (`individual-1v1`/`team-3v3`, incl. Flex) as of 2026-09-28 — a head-to-head room shape cuts only 1 unit per round, too slow to reach a Final above 16 units (see "Kings Valley: gate out head-to-head formats" in `HANDOFF_LOG.md`); gated at generation and hidden in Setup, but tournaments generated before the gate keep working. See "Kings Valley: gate out head-to-head formats" in `HANDOFF_LOG.md`. As of 2026-09-27 (see "Kings Valley lone units" in `HANDOFF_LOG.md`), a room left with fewer than 2 real occupants (a removal, or an odd head-to-head field) **holds**: it promotes and cuts nobody, its unit(s) simply keep their ladder position into next round. The elimination cut always comes from the *effective bottom* — the last room (by ladder position) that still has a real match — which is not necessarily the literal last room, since a lone room can end up anywhere, including below it. One shared band rule (`kingsValleyRoomBandCounts`, `kings-valley.ts`), computed from each room's real size, drives generation, the real advance and the Bracket exit chips identically. Whenever a removal or a reserve leaves the real survivor count reaching a Kings Valley round different from what was planned, the rest of the ladder (through the Final) is re-planned to the real count (`fitKingsValleyTail`, `transitions.ts`) instead of seeding too few or silently dropping the extra. **`waterfall-bracket`** (new, 2026-09-21, supersedes `ROADMAP.md` items 7 & 8) — an entirely organiser-authored, generation-time-only rank-band routing bracket: the organiser types a `ROUNDS:`/`ROUTES:` mini-language into a Setup textarea (`src/domain/tournament/waterfall-bracket.ts` parses/validates it) describing an arbitrary round graph where each room's finishers split by rank into bands, each band routing to its own destination round — not necessarily the next one, and not necessarily all to the same place, so a room's own top-4 can skip several rounds straight into a semifinal room while its 5th–8th feed a consolation room several other rooms also feed into. No live reseeding, no bye/lucky-loser handling, reserves blocked entirely once the tournament starts. Authored through a click-to-route table in Setup (`src/features/admin/waterfall/`), which reads and writes that same text. Known live-verified UX characteristic, not a bug: Rankings can transiently show an actually-still-alive unit as "eliminated" for one round, whenever its real destination round hasn't been finalized yet — self-corrects the moment that round is actually reached; identical, pre-existing timing to double-elimination's own deferred-LB-target case. See "Waterfall / rank-band bracket phase" in `HANDOFF_LOG.md`.

**Semis/Final**: both support multi-game scoring (1–4 games, summed) via the "Finals format"/"Semis format" setup fields — same underlying mechanism as legacy (Final: `T.finalScores`/flat pool; Semis: `T.scores` extended with a `-g{n}` key segment, room-based).

**Scoring**: two systems, organiser-selectable per tournament whenever `poolingPhase !== 'none'` (`ScoringSystemKey = "fairpoints" | "positional-points"` — "Raw score only" was already removed pre-rework and stayed removed). **Fair Points** (default): `fairPoints(rank, score) = rank - score / 100_000` — lower is better, a higher score wins a same-rank tie (confirmed directly in `src/domain/tournament/scoring.ts:150-152`); cumulative `totalFP` is *averaged* across rounds played. Averaging has no volume discount, a deliberate tournament-design trade-off (settled with the organiser 2026-09-17): a unit that played only 2 rounds (the minimum a qual-table/Swiss reserve can end up with, given the reserve-admission guard under "Pooling phases") is compared on equal footing with one that played every round, so a small, lucky sample can outrank a longer, more consistent record. Bayesian shrinkage (blending each average with the field average by rounds played) would smooth this out but was rejected as too opaque, with no obviously-correct tuning constant — see "Fair Points: sum → average, plus a reserve-admission guard for qualification-table/Swiss" in `HANDOFF_LOG.md`. A room with exactly one assigned unit (its opponent was removed, or an odd unit was left alone) is not a match and, like a bye, is left out of the standings entirely (`isUncontestedRoom`, `advancement.ts`), so it changes neither the unit's average nor its played count; the unit still advances and Bracket shows it with a "no opponent" note instead of a score input. **Positional Points** (new, 2026-09-20, `ROADMAP.md` item 5): an organiser-supplied fixed rank-to-points table (`positionalPointsTable`, comma-separated, highest rank first, e.g. "10,8,6,5,4,3,2,1", validated to cover the format's largest possible room size and to never increase rank-to-rank) — higher is better, and cumulative points are *summed* not averaged, matching a real organiser spreadsheet's own convention (summing a per-round value that's already bounded at 0 naturally penalizes a smaller sample, unlike Fair Points, which needs averaging for that same reason). Both systems share `materializeStandings`/`computeQualificationStandings`/`computeGroupStandings` (`advancement.ts`) via a single scoring-aware branch — the one subtlety was that Fair Points is lower-is-better while positional points is higher-is-better, requiring a `compareStandingValue()` helper at exactly the two places that hard-code a sort direction (everything else that reads `totalFP` — tie-cutoff detection, dense ranking — turned out to already be direction-agnostic). Deliberately scoped to qual-table/Swiss/Group-Stage standings only — Semis/Final have no rank-based scoring at all today (raw score sum) and were left out of scope, not half-built. See "Positional-points scoring" in `HANDOFF_LOG.md`.

## Room reseeding
`src/domain/tournament/seeding.ts` holds several distinct mechanisms for deciding which room a player/team lands in next round. Documented here in plain language so a future session can reason about "how did this person end up in this room" without re-deriving it from the code:

- **`randomSeed`** — Round 0 only (initial roster → Round 1 rooms). A true shuffle via the injectable `RandomSource`.
- **`swissFoldPair`** — Swiss pooling rounds. Fold-pairs by rank (rank 1 vs. rank `half+1`, etc.), with a rematch-avoidance swap applied when one exists that clears both pairs at once.
- **`sequentialSeed`** — takes an already-ordered flat list and slices it directly into a target round's pre-declared room sizes, with no reordering/bouncing. Used for Kings Valley's every room-to-room ladder movement, including the one-time hop into Kings Valley's first round — chosen there specifically so every room always shows exactly as many slots as its declared size (no stray dash, no silent overflow). As of 2026-09-17, no longer used for Bracket's future-round *display projection* (see `distributeTierMajorPool` below) — see "Fix: future-round Bracket placeholders clustered by rank instead of spreading" in `HANDOFF_LOG.md`.
- **`distributeTierMajorPool`** (new, 2026-09-17) — the mechanism behind Bracket's future-round *display projection* (`projectFutureRoundSlots`), replacing `sequentialSeed` at that one call site. The projection still builds its candidate pool tier-major (every room's own rank-1 finisher, then every room's own rank-2, ...) — fixed 2026-09-15 to stop same-room-shape targets from collapsing to exact same-room carryover — but a plain sequential chop of that pool had its own residual flaw: whenever a target room's size spans more than one source room's worth of a single tier (a small source-room count feeding a large target room), the first target room could swallow two or more whole rank-tiers before the chunk boundary ever reached a lower rank, showing e.g. only Rank 1/2 finishers and no Rank 3+ — reported live on a real tournament. `distributeTierMajorPool` round-robin-assigns each tier's own entries across target rooms with remaining capacity, rotating the round-robin's starting room by one every time the tier changes, so every room gets a spread across ranks *and* source rooms instead of a homogeneous block. Same accepted tradeoff as before (unchanged in spirit): every projected slot still matches its own room's declared size exactly, but the exact target-room assignment can still drift from what the real transition (`tieredSeed`/`tieredBracketSeed`) eventually produces once the round is actually reached. See "Fix: future-round Bracket placeholders clustered by rank instead of spreading" in `HANDOFF_LOG.md`.
- **`snakeSeed`** — the original, simpler room-reseeding mechanism: takes advancing candidates ordered room-major/rank-minor (each room's own survivors best-to-worst, room by room) and distributes them into target rooms via a boustrophedon (zig-zag) bounce. As of 2026-09-12, **not called anywhere in the live app** — both places that used it (the generic transition path, and double-elimination's WB/LB routing) now use `tieredSeed`/`tieredBracketSeed` instead. Kept as an exported, unit-tested primitive rather than deleted.
- **`tieredSeed`** (new, 2026-09-12) — replaces `snakeSeed` at the one call site in `transitions.ts` that drives every *ordinary* room-based transition: no-elim warm-up rounds, Qualification Table, and real single-elimination/team-format cutting rounds, up to and including the round that decides Semis' own room composition. Built to fix two real problems the organiser identified by hand-simulation of `snakeSeed`'s old behavior: (1) **extremes-clustering** — a room's own best and worst finisher could fold together into the very same next room regardless of true global standing; (2) **round-to-round staleness** — the same players kept landing in the same room together round after round once standings stabilized (verified up to 8/8 unchanged room membership by round 5-6 in a 32-player no-elim simulation).

  **How it works, in plain terms**: instead of listing survivors room-by-room, `tieredSeed` groups them into *rank tiers* spanning every room at once — tier 0 is every room's own winner, tier 1 is every room's own runner-up, and so on. (A room's own within-room dominance margin, `pct`, is used only to break a tie *within* the same tier, never to compare across tiers — a room's winner's margin only says something about that room's specific opponents.) It fills the next round's rooms one "wave" at a time (a wave is one tier, or a partial tier when room sizes are uneven), and for each wave it assigns that small group of candidates to the available rooms by picking the assignment that minimizes a weighted cost of (a) recency-weighted repeat-pairs against everyone already placed this reseed and every prior round's history, and (b) how far each room's running total would land from perfectly balanced. A pairing that last shared a room the round before gets a mild ~10% cost premium over one that hasn't shared a room in many rounds — enough to nudge the search away from the very freshest repeats without ever letting that override balance. The diversity-vs-balance weighting itself shifts smoothly over the bracket: heavily diversity-weighted during no-elim warm-up and the earliest real cutting rounds, shifting to heavily balance-weighted by the round that seeds into Semis — so a spot in the Final stays decided by skill and results, not by forcing together players who simply haven't played each other yet. (The Final itself is always a single room, so there's nothing left to taper by that point.)

  A new persisted state field, `roomHistory: Record<string, number>` (a canonical pair-key → the round index that pair most recently shared a room), tracks match history across the whole tournament — mirrors the existing `poolingByeCounts` field's shape and update pattern.

  **Scope, explicit**: only the one `transitions.ts` call site described above. Kings Valley's own ladder movement (`sequentialSeed`, not a global reseed at all) is untouched by this change.

- **`tieredBracketSeed`** (new, 2026-09-12) — the same diversity/recency/taper mechanism extended to double-elimination's WB/LB routing (`finalizeDoubleEliminationRound`, both the `race` and `shared-final` variants — the one remaining `snakeSeed` call site). Structurally different from `tieredSeed` because a target round's pool there can accumulate from **more than one source round** (a losers-bracket round routinely pools a WB round's fresh drops together with the previous LB round's own survivors) — `buildAdvancementTiers` only ever handles one source round at a time. Resolved by tagging each contribution's room-rank tier at the moment it's pushed (`advanceDoubleElimination`, one source round at a time, while a single `buildAdvancementTiers` call is still valid), so by the time the pool is finalized every entry already carries a directly comparable tier number regardless of provenance. Uses a new taper, `doubleEliminationApproachProgress` — computed **per bracket side** (WB and LB independently approach one shared terminal round, unlike the generic path's single linear ladder), with the terminal round (Grand Final, or the shared-final variant's untagged terminal Final) always at progress 1. `assignWaveToRooms`/`recencyWeight`/`roomHistory`/`recordRoomHistory` are all reused completely unchanged — `roomHistory` is one global map, so a WB-round rematch is already correctly visible to LB-round avoidance with no extra wiring. Double-elimination rounds now write to `roomHistory` too, closing a gap where they previously never did. See "Extend diversity + rematch-aware reseeding to double-elimination's WB/LB routing" in `HANDOFF_LOG.md` for the full design/testing account, including one disclosed, accepted test-coverage gap (the `targetRoundIndex` convention at this call site is verified by direct reasoning, not a dedicated adversarial mutation test).

  See "Diversity + rematch-aware room reseeding" in `HANDOFF_LOG.md` for the full design rationale, algorithm derivation, and testing account.

  **Behavior worth knowing when explaining this to players** (found 2026-09-21 by running the real `assignWaveToRooms` on synthetic brackets — see "Seeding system explainer + seeding-behavior findings" in `HANDOFF_LOG.md`): the balance term is often an exact tie — whenever every candidate in a wave shares the same tier rank, and for *any* two-room destination starting from zero totals — so the automatic taper acts almost identically to pure `diversity` in common bracket shapes; balance visibly bites only in reseeds with 3+ destination rooms. And a pure `balance` override (diversityWeight exactly 0) ignores repeat history entirely (ties go to the lexicographically first room sequence) rather than merely weighting it down, so it can produce *more* repeat opponents than a balance-heavy-but-nonzero blend.

- **Fixed-draw scheduling** (new, 2026-09-20, `src/domain/tournament/fixed-draws.ts`) — an entirely separate mechanism from everything above, used only when a qual-table/Swiss tournament opts into `gamemodeConfig.drawPublication === 'fixed'` (Setup's "Draw publication" field, default `'adaptive'`). Computes the *whole* room schedule once at generation time from roster order alone — never from live results — instead of reseeding round to round. Swiss reuses `circleMethodSchedule` (the same pairwise round-robin primitive Group Stage's own schedule already uses) directly, guaranteeing zero repeat pairings. Qual-table (room size can exceed 2) uses a new greedy wave-based fill reusing `assignWaveToRooms` — the same room-choice primitive `tieredSeed` itself uses — with every candidate's tier rank held constant (there's no live skill signal to balance in a fixed draw), matching `tieredSeed`'s own accepted quality bar rather than exceeding it. The result is stored per-round on `TournamentRound.fixedRoomAssignments`, not pre-populated into `state.assignments` (which is used elsewhere as the "this round has been reached" signal — see `rankings.ts`'s `lastAssignedRound`) — mirroring Group Stage's own `matches`/`groupByes` precedent exactly. `transitions.ts` reads it directly when present, bypassing `tieredSeed`/`swissFoldPair` entirely; `roomHistory`/`poolingByeCounts` for the whole fixed schedule are folded in at generation time so the live transition out of the pooling phase still avoids rematches against the fixed rounds. A removal or swap after generation patches the not-yet-reached fixed rounds (a removed unit's opponent gets a bye, rooms are renumbered) and rebuilds `roomHistory`/`poolingByeCounts` from them, added 2026-09-25 (#46). See "Pre-published, fixed multi-round draws" in `HANDOFF_LOG.md`.

## Admin access
Real per-user authentication against Curve Fever Pro accounts, replacing the legacy single-shared-password model entirely.
- **Login**: `CfpLoginModal` collects email + password, `AuthProvider.login()` calls the CFP API's `/auth/login` (`src/lib/api.ts`).
- **Authorization**: `auth.shared.ts` defines account roles and an allowlist `TOUR_ADMIN_ROLE_IDS = [ADMIN, MOD, LEAD_MOD, DEVELOPER, TOUR_HOST, LEAD_TOUR_HOST]`; `canAdminTour(roles)` checks the logged-in account's roles against it.
- **Session**: access token stored in a cookie + `localStorage` (30-day max age). On every SSR request, `getInitialAuth` (`server/auth.server-fns.ts`) re-validates the token against the CFP API (60s in-memory cache) and only returns an authenticated snapshot if `canAdminTour()` passes.
- **Server-side enforcement**: every privileged write calls `requireTourAdminPermission()` (`tour-permissions.server.ts`), which re-derives the caller's role from their session cookie **on the server**, fresh, every time — not trusted from client-reported state.
- Legacy `localStorage` flags (`curveFFA_admin_unlocked`, `curveFFA_admin_proof_hash`) are actively deleted on hydrate; nothing from the old scheme survives.

**Read access to live tournament data stays fully public** (`database.rules.json`: `tournaments/$id` → `.read: true`) — same model as legacy (a shareable link *is* the access boundary for viewers); only writes got the auth upgrade. Worth keeping in mind — it means a guessed/leaked tournament ID can be read by anyone, unauthenticated, same as before.

## Sync & persistence
- **Writes**: browser calls `writeTournament()` (`tournament-write.server-fns.ts`, a TanStack Start server function) → validates the tournament ID, strips any legacy `adminProof` field, calls `requireTourAdminPermission()`, then writes via the Firebase **Admin** SDK (service account) — `database.rules.json` denies direct client writes outright (`.write: false` everywhere). This is the one structurally new piece: legacy wrote straight from the browser, gated only by a DB security-rule hash check.
- **Reads**: still direct client-side Firebase reads (`firebase-client.ts`, `onValue`), public/unauthenticated — a viewer link needs no login, matching legacy.
- **`SyncCoordinator`** (`live-sync.ts`): otherwise architecturally the same as legacy — writer/viewer mode split, debounced push (400ms default), the same null↔sentinel marshal/unmarshal to survive Firebase's array-null-pruning bug (legacy fix, ported), extended 2026-09-26 (#52) with `{__ffaEmptyArray: true}` and `{__ffaEmptyObject: true}` markers because Firebase also deletes empty arrays and objects and hands a sparse array back as an object (`marshalForFirebase`/`unmarshalFromFirebase`), dirty-key tracking so an in-flight remote update can't clobber a field being actively typed.
- **Fallback**: fully standalone if Firebase is unreachable — `getFirebaseSyncTransport()` returns `null` on failure, UI shows an explicit "Live sync unavailable" state rather than breaking; `TournamentProvider` hydrates from `localStorage` (`curveFFA_state_v1`) regardless.
- **Client-side Firebase config** (`firebase-client.ts`) is hardcoded, not env-sourced — normal for Firebase's client SDK (not a secret key), but worth knowing so it's never mistaken for a leaked credential.

## Design intent for viewer-facing tabs
Carried forward unchanged from the legacy app's own design-exploration rounds — still the standard to judge new viewer-facing work against:
- **No live events, no audience, no stream overlay.** Every player plays online, alone, at their own computer.
- **Two real success criteria for a viewer**: (1) **convenience** — instantly seeing, zero clicks, which room you're in and who you're facing; (2) **fun/engagement** — seeing how the rest of the tournament is doing.
- **Scoreboard serves neither** — it's admin tooling, not a viewer destination.
- **No staggered reveal** — every score reaches every connected viewer at the same instant.
- **"Follow a player," never "who are you."** Anyone — a player following themselves, a spectator, an admin — can follow any name.
- **A collapsed round is a display state, not a data reduction.** Reopening must show the exact same detail the current round's display uses.
- **Future rounds default to fully visible**, not collapsed or faded — a viewer *may* manually fold any round, current/future included, but the app never imposes that by default.

## Core value
The app's core value is handling "uncomfortable" registration numbers automatically. Whatever the player count — 31, 37, 43, 53 — the app should calculate the optimal room distribution, advancement numbers, and lucky loser count without the organiser needing to think about it. ## Open items

For larger forward-looking projects and architectural work, see `ROADMAP.md`. The items below are smaller-scope, shorter-horizon open questions and known gaps.

**Display/UX gaps** (awaiting organiser feedback):
- **Rankings' compact per-unit rank badge vs. Scoreboard's full standings table** — two different levels of detail for the same "where do I stand" question (Rankings: one-line `#rank · X.XXX FP`; Scoreboard: full Pos/Player/FP/Score/Played table). Both currently judged legitimate at their own fidelity; open question is only whether the organiser ever finds the two views inconsistent or wants them consolidated into one.

**Known, accepted limitations** (not building without organiser request):
- **Anonymous Finals don't support grand-final (race) rounds or team formats** — Deliberate v1 scope, not an oversight (see "Anonymous Finals matches, v1" in `HANDOFF_LOG.md`). Grand-final race progression (`progressGrandFinalRace`, `finals.ts`) decides when to open the next game by reading the two real finalists' own score keys directly; a game scored under a placeholder alias instead would stall the race forever, so flagging one is a no-op there. Team-format Finals are excluded because `getFinalUnitScore`'s team branch reads a real `TournamentTeam` object via `buildTeamMap()`, which a placeholder alias never has. Both would need dedicated follow-up work, not a half-built extension of v1.
- **`cn()` doesn't deduplicate conflicting Tailwind utility classes** — Found 2026-09-18 while fixing a Bracket score-input overflow bug. `cn()` (`src/components/ui/cn.ts`) is a plain string-join, not a Tailwind-merge; when a component's several layers each pass a conflicting same-property utility (e.g. `Input`'s shared `w-full`, then `ScoreInput`'s own default `w-22.5`, then a caller's `w-13`), all of them land in the DOM class list simultaneously and the browser's CSS cascade — not class-attribute order — decides the winner, independently *per property*. Worked around locally for the one reported case only (`compactScoreClass` in `BracketView.tsx` now uses Tailwind v4's `!` important suffix on every conflicting utility, guaranteeing it always wins) rather than fixing `cn()` itself — a true fix (e.g. adopting `tailwind-merge`) is a cross-cutting change out of scope for a same-session bug fix. Hit twice more, 2026-09-27, building the exit-chip `Badge`s (`RoomExitChips`/`RoundExitSummary`): `Badge`'s own `uppercase`/`tracking-[0.08em]`/`whitespace-nowrap` beat a caller's `normal-case`/`tracking-normal`/`whitespace-normal` regardless of class order, rendering chip text in all-caps and letting a long chip overflow its column instead of wrapping — same `!` fix both times. **Fix planned 2026-09-28** (organiser's request): make `cn()` merge conflicting utilities, then drop the `!` workarounds.
